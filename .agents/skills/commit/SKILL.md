# 커밋

사용자의 커밋 요청을 실행 권한으로 간주한다. 변경사항을 분석하고 한국어 커밋 메시지를 작성한 뒤, 별도의 승인 질문 없이 커밋한다.

## 절차

1. **변경사항 분석**
   - 대상 저장소에서 `git status --short`, `git diff`, `git diff --cached`로 미스테이징 및 스테이징 변경사항을 모두 확인한다.
   - 추적되지 않은 파일은 내용을 별도로 확인한다. 변경사항이 없으면 알리고 종료한다.
   - 사용자가 지정한 범위를 우선하고, 기존에 스테이징된 변경도 자동으로 포함하지 않는다.
2. **논리적 단위로 분류**
   - 같은 목적의 코드, 테스트, 문서를 하나의 커밋으로 묶는다. 독립적인 변경은 분리한다.
   - 같은 파일의 변경이라도 목적이 다르면 필요한 경우 부분 스테이징으로 나눈다.
3. **한국어 메시지 작성**
   - 형식은 `type: 한국어 요약`으로 작성하고, 실제 변경 내용에 맞는 유형을 선택한다.
     - `feat`: 기능 추가
     - `fix`: 버그 수정
     - `refactor`: 동작 변경 없는 코드 구조 개선
     - `chore`: 설정, 의존성, 문서 등 유지보수
   - 예: `feat: 컴포넌트 미리보기 기능 추가`
   - 커밋별 포함 파일, 변경 요약, 메시지를 정리하고 바로 다음 단계로 진행한다. 계획이나 메시지에 대한 별도 승인을 요청하지 않는다.
4. **커밋 실행**
   - 요청 범위의 파일 또는 변경 부분만 스테이징한다. 기존 스테이징 내용이 범위 밖이라면 이를 보존하고 해당 내용이 커밋에 섞이지 않도록 한다.
   - `git diff --cached`로 실제 커밋 대상을 다시 확인하고, 작성한 메시지로 `git commit`을 실행한다. 분석 이후 변경사항이 추가되면 다시 확인하여 요청 범위에 해당하는 내용만 포함한다.
   - 실패하면 원인을 알리고 중단한다. 훅을 우회하거나 요청 범위를 임의로 넓히지 않는다.
   - 커밋 후 `git status --short`를 확인하고 커밋 해시, 메시지, 남은 변경사항을 보고한다.

푸시, 기존 커밋 수정(amend), 이력 재작성은 일반적인 커밋 요청에 포함되지 않는다.
